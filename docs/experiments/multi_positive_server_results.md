# FashionIQ 多正监督：服务器初步实验

日期：2026-10-14。两组完整训练和评估均已完成。

**结论：当前版本未改善主指标，不建议替换现有 v7 模型。**
它验证了多正标签、额外正例采样与训练损失的接入，但尚未证明检索收益。

## 实验条件

- FashionIQ Dress：5985 条训练查询，2017 条验证查询，完整 3817 张验证图库。
- `original-split`；验证时剔除参考图；官方验证 target 保持原样。
- 两组使用相同 DQU checkpoint 初始化，冻结 DQU，仅训练原有结构化分支。
- Qwen 3.7 Flash 结构化 train/val JSON，DQU 写字图输入，不启用生成图片或双写字图路线。
- seed 42，batch size 16，学习率 5e-5，各训练 6 个完整 epoch；无批次或评估数量截断。
- 两轮 gate 预热，四轮 adapter 训练；相同优化器与正则配置。
- `hard-negative-weight=0` 与 v7 配置对齐；本次未评估非零难负样本项的性能贡献。
- 训练使用 BF16，检索评估使用 FP16，与项目已有协议一致。
- Python 3.10.8，PyTorch 2.9.0+cu128，OpenCLIP 2.23.0。
- 服务器报告 GPU 为 NVIDIA GeForce RTX 4080 SUPER，显存 32760 MiB。
- 训练代码来自提交 `5080813`；两组实际源码 SHA256 完全一致，记录在结果 JSON。

服务器上的 17 项单元测试全部通过；训练中没有非有限损失、非有限梯度或 OOM。
两组运行完成后 GPU 已空闲。服务器原始数据、旧模型和 `main` 代码目录未被覆盖。

## 普通三元组如何形成多正标注

不修改原 JSON，而是在训练时建立额外映射。
若已有三元组 `(参考图 R, 修改文本 T, 目标 A)` 与 `(R, T, 目标 B)`，
就为相同的 `(R, T)` 建立正例集合 `{A, B}`。
T 使用项目原有纠错和拼接规则，随后要求精确相同；不按语义相似度跨查询合并。

| 类别 | 训练查询 | 有不同正例目标的查询 | 覆盖率 |
|---|---:|---:|---:|
| dress | 5985 | 55 | 0.9190% |
| shirt | 5988 | 96 | 1.6032% |
| toptee | 6027 | 38 | 0.6305% |

Dress 的 55 条查询来自 26 个等价组，共有 6049 条可用正例关系。
本次每条多正查询每次额外抽取一张正例；训练日志每轮的实际覆盖率均为 0.009190，
平均目标候选库大小为 16.11。没有额外正例的槽位在目标编码前删除。

三个类别的原始 train target ID 全部唯一，因此单独开启 `identity` 不改变原 batch 的正例关系。
在得到这一审计结果后，取消其完整 GPU 重复训练；其损失退化关系已由单元测试覆盖。

55 条之外的查询仍只有一个已标注目标。本次没有新增人工标签，没有自动挖掘伪正例，
也没有把所有相似裙子当成正样本。`verified` 文件入口已实现，但本次没有使用。

## 如何解释结果

这是单种子、六轮的初步对照，主指标未提高，不能声称此版本优于 v7，
也不能据此否定所有多正样本方法。R@1 的轻微增加并未转化为 R@10 的提高。

覆盖率低、已有等价组中存在疑似噪声，是后续值得检查的因素，但尚未通过消融证明其因果作用。
审计示例中包含“不是服装”“商品图片是文字”等描述；格式有效的 Qwen JSON
不等于三元组的真实相关性已被审核。

本次联合改变了正例损失、门控教师和额外正例采样，没有拆分这些部件的独立贡献。
官方验证仍只有一个 target，因此也不能据此判断多答案相关性指标的变化。

建议后续先在 train 内挖掘候选，用 add/remove/relations 和应保留特征进行语义复核，
剔除疑似噪声后建立覆盖更大的 `verified` 标签文件；在训练开发子集固定策略，
再进行三种子验证。若建立多答案评估，应单独人工复核各方法候选池，并保留官方指标对照。
